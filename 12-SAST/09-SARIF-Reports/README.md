# SARIF Reports

## Learning objectives

By the end of this module, learners should be able to:

- Explain SARIF and its role in static application security testing (SAST).
- Understand the structure of a SARIF 2.1.0 document.
- Read tool metadata, rules, results, locations, fingerprints, and code flows.
- Generate SARIF reports using CodeQL and other compatible scanners.
- Validate and process SARIF safely.
- Upload compatible third-party SARIF results to GitHub code scanning.
- Troubleshoot missing, duplicated, or incorrectly mapped alerts.

## 1. What is SARIF?

SARIF stands for **Static Analysis Results Interchange Format**. It is a JSON-based standard for representing results from static analysis tools. It provides a common structure for reporting findings from SAST scanners, linters, and other code-analysis tools.

SARIF can include:

- Tool and driver metadata.
- Rule identifiers and descriptions.
- Result messages and severity levels.
- File locations and line/column ranges.
- Related locations and code-flow paths.
- Fingerprints used to help identify findings across scans.
- Invocation details and analysis properties.

GitHub code scanning supports a subset of SARIF 2.1.0. A valid general SARIF document is not automatically guaranteed to meet every GitHub ingestion requirement.

## 2. Typical SARIF workflow

1. Run a static analysis tool.
2. Export results in SARIF format.
3. Validate JSON syntax and SARIF schema.
4. Check file paths, rule IDs, locations, and result metadata.
5. Sanitize or protect the report because it may contain sensitive code details.
6. Upload to a compatible code-scanning platform or retain it as a CI artifact.
7. Review alerts, fix issues, and compare subsequent scans.

If GitHub's CodeQL default setup or CodeQL action is used, results are normally uploaded automatically; a separate manual SARIF upload step is not needed.

## 3. SARIF document structure

A SARIF 2.1.0 document commonly contains:

```json
{
  "version": "2.1.0",
  "$schema": "https://json.schemastore.org/sarif-2.1.0.json",
  "runs": [
    {
      "tool": {
        "driver": {
          "name": "ExampleScanner",
          "rules": []
        }
      },
      "results": []
    }
  ]
}
```

Important top-level properties:

| Property | Purpose |
|---|---|
| `version` | SARIF version |
| `$schema` | Schema used to validate the document |
| `runs` | One or more analysis runs |

Each run describes a tool invocation and its results.

## 4. Important SARIF fields

| Field | Purpose |
|---|---|
| `tool.driver.name` | Scanner name |
| `tool.driver.version` | Scanner version |
| `tool.driver.rules` | Rule definitions |
| `results` | Findings produced by the run |
| `ruleId` | Rule identifier for a finding |
| `level` | Result level such as `error`, `warning`, or `note` |
| `message.text` | Human-readable finding message |
| `locations` | Primary code locations |
| `physicalLocation.artifactLocation.uri` | File path or URI |
| `region.startLine` | Starting line |
| `codeFlows` | Data-flow or execution path information |
| `partialFingerprints` | Identifiers that help track results across runs |

A rule definition usually belongs in `tool.driver.rules`; a result refers to it through `ruleId` or `ruleIndex`.

## 5. Severity and level

SARIF's `level` values are not a universal CVSS score. Tools may also use rule properties or tags to convey security severity and other metadata.

Common levels:

- `error`
- `warning`
- `note`
- `none`

Do not assume that every scanner maps its severity scale to SARIF levels in the same way. Review the scanner's SARIF export documentation and the destination platform's supported properties.

## 6. Locations and paths

A result location typically identifies an artifact (such as a source file) and a region (such as a line range). Paths should be stable and map correctly to the repository checkout.

For GitHub code scanning, relative paths are generally preferable. Incorrect absolute paths or mismatched checkout roots can prevent annotations from appearing at the expected source lines.

## 7. Code flows

A SARIF result may contain `codeFlows`, which can describe a path through related locations. This is especially useful for data-flow findings:

- Source: untrusted input.
- Intermediate steps: assignments, function calls, and transformations.
- Sink: sensitive operation.

Not every scanner includes code flows, and not every finding needs them.

## 8. Fingerprints and duplicate alerts

Fingerprints help platforms correlate results between scans. GitHub can calculate `partialFingerprints` for uploaded SARIF when the required source context is available, but stable fingerprints generated by the scanner can improve correlation.

When uploading multiple result sets for the same commit, use distinct categories/identifiers as required by the upload method. Reusing a category for the same tool can cause a later upload to replace earlier results.

## 9. Generate SARIF with CodeQL CLI

Example for a previously created Python database:

```bash
codeql database analyze db-python \
  codeql/python-queries \
  --format=sarif-latest \
  --output=codeql-results.sarif
```

`--format=sarif-latest` selects the SARIF format supported by the installed CodeQL CLI for the target integration. Confirm compatibility with your destination platform and CLI release.

## 10. Validate a SARIF file

First validate JSON syntax:

```bash
python -m json.tool results.sarif > results-pretty.json
```

Then validate against the SARIF 2.1.0 schema or a compatible validator. Schema validation checks structure; platform-specific ingestion validation may impose additional requirements.

Example using Python to inspect a report:

```python
import json

with open("results.sarif", encoding="utf-8") as file:
    report = json.load(file)

assert report.get("version") == "2.1.0"

for run in report.get("runs", []):
    driver = run.get("tool", {}).get("driver", {})
    print("Tool:", driver.get("name"))
    for result in run.get("results", []):
        print(
            result.get("ruleId"),
            result.get("level"),
            result.get("message", {}).get("text")
        )
```

Treat SARIF as untrusted input when processing reports from external tools. Avoid executing content embedded in messages or properties.

## 11. Upload third-party SARIF to GitHub

A GitHub Actions workflow can upload a SARIF file generated by a third-party scanner using the official `upload-sarif` action.

Example outline:

```yaml
name: Upload SARIF

on:
  push:
    branches: [main]

permissions:
  contents: read
  security-events: write

jobs:
  upload:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: reports/results.sarif
          category: third-party-sast
```

This assumes the report already exists at the specified path. Add the scanner execution and artifact generation steps as appropriate. For high-assurance workflows, pin actions to full commit SHAs and review current action versions.

GitHub code scanning availability depends on repository type and product/organization settings. Check the current GitHub documentation before planning private-repository ingestion.

## 12. Upload using the CodeQL CLI

For supported CodeQL CLI workflows, results can be uploaded with:

```bash
codeql github upload-results \
  --sarif=codeql-results.sarif \
  --repository=OWNER/REPOSITORY \
  --ref=refs/heads/main \
  --commit=COMMIT_SHA
```

Authentication must be supplied securely using the supported CLI options or environment. Do not hardcode tokens in scripts, workflow files, or command history. The token needs the appropriate code-scanning/security-events permission.

## 13. Common errors

| Symptom | Likely cause / checks |
|---|---|
| Invalid JSON | Truncated or malformed report |
| Unsupported SARIF version | Destination requires supported SARIF 2.1.0 subset |
| Alerts have no source annotation | Incorrect URI/path or region |
| Duplicate alerts | Unstable/missing fingerprints or categories |
| Results overwritten | Same tool/category used for multiple uploads |
| Upload rejected | Permissions, feature availability, size limits, or schema incompatibility |
| No results displayed | Empty results, wrong branch/commit, processing delay, or unsupported fields |

## 14. Security and privacy

SARIF may expose repository paths, snippets, vulnerability details, and internal architecture. Protect it like source-code security data:

- Restrict artifact access.
- Avoid publishing reports from private repositories.
- Set appropriate artifact retention.
- Do not include secrets in custom messages or properties.
- Review third-party scanner output before uploading.
- Use least-privilege upload permissions.

## 15. Best practices

- Generate SARIF consistently in CI.
- Use stable rule IDs and meaningful descriptions.
- Prefer repository-relative paths.
- Include accurate line/column regions.
- Preserve useful fingerprints.
- Use unique categories for separate analysis streams.
- Validate reports before upload.
- Keep tool and SARIF format versions documented.
- Protect reports and credentials.
- Track alert trends across scans.
