# Suggested Solutions and Review Notes

Solutions are examples. Review decisions must reflect the actual code, architecture, threat model, and organization policy.

## Lab 1 — Invoice download API
Important checks: authentication, per-object authorization, tenant isolation, safe file retrieval, rate limiting, audit logging, and negative tests. A valid finding explains that login alone does not authorize access to every invoice. The fix belongs on the server and should be covered by tests for same-owner access and cross-owner denial.

## Lab 2 — Password reset
Good controls include cryptographically secure random reset tokens, limited expiry, single-use semantics, secure storage (for example, a hash of the token), rate limiting, generic account-enumeration-resistant responses, and invalidation of existing sessions when policy requires. Logs must not contain reset tokens. Test expired, reused, malformed, and cross-account tokens.

## Lab 3 — Dependency update
Check the exact package identity, repository/source, version, lockfile, maintenance status, known vulnerability information, licenses, transitive dependency changes, and install-time behavior. A scanner result is evidence to triage, not an automatic complete risk assessment. Record approval or the specific remediation needed.

## Lab 4 — CI/CD
Untrusted pull-request jobs should not receive production secrets or broad write permissions. Separate validation from deployment, restrict deployment to trusted branches/tags and approved environments, pin/review actions, limit token permissions, and ensure artifact provenance. Test the workflow's behavior under forked pull requests and unexpected branch conditions.

## Lab 5 — File upload
Possible abuse cases: oversized upload, extension/content mismatch, malicious file, path traversal in filename, archive expansion, direct access to quarantine, cross-user download, stored XSS in served content, and resource exhaustion. Defenses include limits, generated names, content inspection, quarantine, safe serving headers, access checks, and monitoring.

## Lab 6 — Infrastructure-as-code
Verify that storage is private by default, access is least-privilege, encryption and logging match policy, and retention/deletion are defined. Review role trust relationships and permissions for wildcard or unnecessary actions. Static analysis can identify many configuration patterns, but deployed effective permissions and network exposure may require runtime verification.

## Lab 7 — Business workflow
Enforce valid state transitions server-side, use transactions/locking or idempotency to handle races and duplicate requests, verify authorization at every step, validate amount and account state from trusted server-side records, and create tamper-resistant audit records. UI-only restrictions are insufficient.

## Lab 8 — Mock review
A complete result includes scope, applicable checklists, evidence-backed statuses, specific findings, severity rationale, owner, due date, decision, and retest evidence. “Looks secure” or “scanner passed” is not enough to establish security.

## Lab 9 — Improving checklist items
Weak: “Is authentication secure?”
Better: “Does every protected route require authentication, and do automated tests verify unauthenticated requests are rejected?”

Weak: “Are uploads safe?”
Better: “Are file size and content validated server-side, filenames generated by the server, and uploaded content stored outside executable web roots?”

A good checklist item is observable, testable, and scoped. Mark technology-specific items N/A only with a reason.

## Self-assessment rubric (20 points)
- Scope and risk identification: 0–3
- Appropriate checklist selection: 0–3
- Evidence-based statuses: 0–4
- Findings and remediation quality: 0–4
- Risk-based decision and escalation: 0–3
- Retest and documentation: 0–3
