# GitLab Pipeline Fundamentals — Solutions and Explanations

> These are reference solutions. Adapt image versions and commands to the runner environment used in your lab.

## Exercise 1: Minimal pipeline

```yaml
hello:
  image: alpine:3.20
  script:
    - echo "Hello from GitLab CI"
```

Commit this file as `.gitlab-ci.yml`. A runner must be available to execute the job.

## Exercise 2: Stages

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  image: alpine:3.20
  script:
    - echo "Build completed"

test_job:
  stage: test
  image: alpine:3.20
  script:
    - echo "Tests passed"

deploy_job:
  stage: deploy
  image: alpine:3.20
  script:
    - echo "Deployment placeholder"
```

**Explanation:** Stages run in declared order. Jobs in a stage can run concurrently when runner capacity permits. A job without `stage` defaults to `test`. A failed job normally prevents later stages from starting.

## Exercise 3: Parallel jobs

```yaml
stages:
  - test

test_a:
  stage: test
  image: alpine:3.20
  script:
    - sleep 5
    - echo "A complete"

test_b:
  stage: test
  image: alpine:3.20
  script:
    - sleep 5
    - echo "B complete"
```

**Explanation:** GitLab can schedule both jobs at the same time, but actual overlap depends on the availability and concurrency of eligible runners. A single runner with concurrency set to one will process them one at a time.

## Exercise 4: Artifact

```yaml
create_artifact:
  image: alpine:3.20
  script:
    - mkdir -p output
    - echo "Artifact generated by CI" > output/result.txt
  artifacts:
    paths:
      - output/
    expire_in: 1 week
```

**Explanation:** Paths are relative to the project working directory. The artifact can be downloaded from the job page. Artifacts are for preserving outputs; caches are primarily for speeding up repeated work.

## Exercise 5: Variables

```yaml
variables:
  APP_ENV: "development"

show_variable:
  image: alpine:3.20
  variables:
    APP_ENV: "lab"
  script:
    - echo "APP_ENV=${APP_ENV}"
```

Expected output includes `APP_ENV=lab`, because the job-level value overrides the top-level YAML value. Never use this pattern to store credentials.

## Exercise 6: Rules

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH'

default_branch_job:
  image: alpine:3.20
  script:
    - echo "Default branch job"
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

merge_request_job:
  image: alpine:3.20
  script:
    - echo "Merge request job"
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

**Explanation:** `workflow: rules` decides whether a pipeline is created. Job `rules` decide whether that job is added to the created pipeline. Rules are evaluated in order.

## Exercise 7: Runner tags

```yaml
tagged_job:
  tags:
    - linux
  script:
    - echo "Scheduled on a runner matching linux"
```

**Explanation:** A runner must be online, enabled for the project, and eligible for the job. If no runner matches the tags and access settings, the job can remain pending.

## Exercise 8: Failure diagnosis

Failing example:

```yaml
failing_job:
  image: alpine:3.20
  script:
    - echo "Starting"
    - exit 1
    - echo "This line is not reached"
```

Corrected example:

```yaml
passing_job:
  image: alpine:3.20
  script:
    - echo "Starting"
    - echo "Command completed"
```

**Explanation:** A non-zero exit status normally marks the job as failed. Inspect the job log to find the first command that returned an error.

## Exercise 9: Configuration validation

Use GitLab's CI Lint tool or pipeline editor to validate GitLab-specific syntax and configuration. A local YAML parser can catch malformed YAML but cannot fully validate GitLab keywords, includes, variables, or pipeline creation behavior.

## Viva answers

1. **GitLab CI/CD:** GitLab's automation capability for building, testing, and deploying software changes.
2. **`.gitlab-ci.yml`:** The default YAML configuration file that defines pipeline workflow, stages, jobs, and related settings.
3. **Pipeline/stage/job/runner:** A pipeline groups jobs; stages group jobs into ordered phases; a job performs a task; a runner executes the job.
4. **Same-stage jobs:** They may run in parallel if enough eligible runner capacity exists.
5. **Job failure:** The pipeline is normally marked failed and later stages do not run, unless configuration changes failure handling.
6. **Cache vs artifacts:** Cache reuses files to speed up jobs; artifacts preserve job outputs and pass them to later jobs or users.
7. **Runner tags:** Tags route jobs to runners with the required capabilities.
8. **`rules`:** Conditions that determine whether a pipeline or job is created and, in some cases, its behavior.
9. **Predefined variables:** Values supplied by GitLab for context such as project, commit, branch, and pipeline source.
10. **Secrets in YAML:** Committed secrets can be exposed in repository history and job logs; use protected/masked CI/CD variables or a secret manager.
