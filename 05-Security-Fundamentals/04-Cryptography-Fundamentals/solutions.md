# Cryptography Fundamentals - Suggested Solutions

Answers are examples. Real implementations should follow current standards, vetted libraries, and the application's threat model.

## Part A: Knowledge Check
1. Plaintext is original data; ciphertext is the result of encryption.
2. Symmetric cryptography uses a shared secret and is efficient for bulk data. Asymmetric cryptography uses a public/private key pair and supports uses such as signatures and key establishment.
3. Encryption protects confidentiality and can be reversed with the correct key. Hashing creates a fixed-size digest and is not designed to be reversed.
4. HMAC verifies integrity and authenticity for parties that share a secret. A plain hash does not prove that a message came from a secret-holding party.
5. A valid signature verifies under a public key and signature scheme. If the public key is trusted and the private key protected, it supports integrity and signer authentication.
6. Base64 is a reversible encoding and requires no secret key.
7. Predictable keys may be guessed or recovered, undermining the algorithm.
8. Disabling TLS validation may allow server impersonation or interception without detection.

## Part B: Select a Mechanism
1. Authenticated encryption with a properly managed key, using a vetted implementation and correct parameters.
2. A cryptographic hash such as SHA-256, with the expected digest obtained from a trusted source.
3. Digital-signature verification using a trusted publisher public key and a defined revocation/trust process.
4. HMAC with a securely shared secret, with protocol protections against replay where needed.
5. A cryptographically secure token API such as Python's `secrets` module.
6. A password-hashing function designed for password storage, such as Argon2id where supported or another current platform-recommended option, with unique salts and appropriate cost settings.

## Part C: Practical Labs

### Lab 1: File Hashing
The digest should change when the file changes, with overwhelming probability. Exact values depend on the file bytes. A hash is useful only when the expected digest is trusted; it does not authenticate the publisher on its own.

### Lab 2: Secure Randomness
Tokens generated by `secrets` should normally differ. Python's `random` is intended for general-purpose pseudorandom use, not security-sensitive secrets. Avoid logging tokens and provide appropriate scope, expiration, secure storage, and revocation.

### Lab 3: HMAC
Changing the message while retaining the old tag should cause verification to fail. Anyone who obtains the shared key can generate valid tags. Use `hmac.compare_digest` for tag comparison.

### Lab 4: Secret Handling Review
Problems include hardcoding a credential, potential exposure through version control, logging the secret, weak rotation/revocation practices, and excessive access. Prefer a suitable secret manager or protected runtime injection, least privilege, no secret logging, and rotation of any exposed real credential. Environment variables are not automatically safe; protect the runtime environment too.

### Lab 5: TLS
Hostname validation checks that the certificate matches the intended hostname. Investigate the hostname, validity dates, certificate chain, trust store, system clock, and server configuration. Fix the cause rather than permanently disabling validation.

## Part D: Scenario Analysis

### Scenario 1: Unauthenticated Encryption
Ciphertext modification may go undetected and can affect decrypted data or application behavior, depending on the scheme. Use a vetted authenticated-encryption construction or protocol. Follow requirements such as nonce uniqueness and correct key management.

### Scenario 2: Compromised Signing Key
- Trigger incident response and restrict further access to the key.
- Identify the exposure window and review build logs, release records, and signed artifacts.
- Revoke or retire the compromised key through the established trust process.
- Rebuild and re-sign trusted artifacts with a new protected key as appropriate.
- Improve key isolation, access control, audit trails, and rotation/revocation procedures.

### Scenario 3: Password Storage
A fast unsalted hash makes offline guessing easier and identical passwords produce identical hashes. Use a password-hashing function designed to be costly to attack, a unique salt per password, and work factors calibrated to current guidance and available infrastructure. Never store plaintext passwords.
