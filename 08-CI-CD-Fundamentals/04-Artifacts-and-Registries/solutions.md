# Solutions — Artifacts and Registries

These are model answers. Adapt tooling and policies to your project, threat model, and registry platform.

## Solution 1 — Artifact types

| Item | Type | Purpose | Sensitivity considerations |
|---|---|---|---|
| `app.py` | Source file | Human-maintained application code | Check for hard-coded credentials or private data |
| `dist/app-1.0.0.whl` | Build artifact/package | Installable Python distribution | Inspect included files and metadata |
| `ghcr.io/example/app@sha256:...` | Container image by digest | Identifies a specific registry image | Restrict pull/push rights as required |
| pip cache | Cache | Speeds up dependency installation | Do not trust it as a release artifact; isolate cache scopes |
| `junit.xml` | Test evidence | Test outcomes | May reveal paths, test names, or internal metadata |
| `sbom.cdx.json` | SBOM | Inventory of components | Can reveal dependency and version details |
| Signed build statement | Provenance/attestation | Evidence linking artifact, source, and build process | Verify signature, identity, subject digest, and policy |

## Solution 2 — Create and hash an archive

Example commands:

```bash
mkdir -p dist
git archive --format=tar.gz --output=dist/source.tar.gz HEAD
sha256sum dist/source.tar.gz
git rev-parse HEAD
```

After changing and committing a tracked file, create the archive again and calculate its checksum. The bytes differ, so the digest will ordinarily differ. Archive metadata can also affect bytes, so use a reproducible-build approach if byte-for-byte repeatability is required.

Record at least the artifact name, source commit, build identity, toolchain/dependency context, checksum, and build timestamp. The timestamp alone does not establish trust.

## Solution 3 — Verify integrity

Linux example:

```bash
sha256sum dist/source.tar.gz
cp dist/source.tar.gz dist/source-copy.tar.gz
printf 'x' >> dist/source-copy.tar.gz
sha256sum dist/source-copy.tar.gz
```

The two checksums should differ because the files differ. For a formal check, put the trusted expected checksum in a file and use `sha256sum --check`.

A matching checksum is evidence that the checked bytes match the expected bytes. If an attacker can replace both the artifact and the expected checksum, the check provides no independent authenticity assurance. Protect the expected value or use a verified signature/provenance mechanism.

## Solution 4 — Versioning design

Example identifiers:

```text
ghcr.io/example-org/web-api:1.8.2
ghcr.io/example-org/web-api:git-7ac91f2e48b1
ghcr.io/example-org/web-api:pr-42-7ac91f2
ghcr.io/example-org/web-api@sha256:<actual-digest>
web-api-1.8.2+7ac91f2e48b1.tar.gz
```

The digest is a placeholder and must be replaced by the real registry digest. Use semantic versions for release intent, commit IDs for traceability, and digests for exact image identity. Protect release tags from overwrite where supported and record the resolved digest in release metadata.

## Solution 5 — Build and inspect a Docker image

Example commands:

```bash
docker build -t demo-app:1.0.0 .
docker image inspect demo-app:1.0.0
docker image ls --digests
```

- **Local image ID:** Identifier for the local image object/configuration in the Docker engine.
- **Tag:** A human-readable name that may be reassigned.
- **Registry digest:** Content-addressed identifier for a manifest or index in the registry.

The precise digest and image ID values are generated by the tools and must not be guessed. After pushing, capture the digest reported by the registry or inspect the pulled repository image.

## Solution 6 — GHCR publishing

Typical workflow, after authenticating using a supported credential with package-write permission:

```bash
docker tag demo-app:1.0.0 ghcr.io/OWNER/demo-app:1.0.0
docker push ghcr.io/OWNER/demo-app:1.0.0
```

Replace `OWNER` and use only a registry namespace you control. Review package visibility and permissions, record the real digest, and verify that the expected identity can pull the image. Do not place credentials in scripts, shell history, or Git.

## Solution 7 — CI artifact upload

Example workflow:

```yaml
name: Package Source

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  package:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Archive tracked source
        run: |
          mkdir -p dist
          git archive --format=tar.gz --output=dist/source.tar.gz HEAD
          sha256sum dist/source.tar.gz > dist/SHA256SUMS

      - name: Upload files
        uses: actions/upload-artifact@v4
        with:
          name: source-archive
          path: |
            dist/source.tar.gz
            dist/SHA256SUMS
          if-no-files-found: error
```

The `git archive` command includes tracked files, not arbitrary untracked files. If a file is required in the artifact, ensure it is tracked and committed. In production, pin third-party actions to verified full commit SHAs.

## Solution 8 — SBOM and provenance flow

One valid design:

1. Build the image from a reviewed source revision in an isolated runner.
2. Run tests, dependency checks, and image scanning.
3. Generate an SBOM for the actual built image.
4. Publish the image and capture its digest.
5. Generate authenticated provenance linking the digest to the source revision and builder.
6. Store SBOM and provenance as release evidence linked to the digest.
7. Before promotion, verify the subject digest, signature/identity, trusted builder, source repository/revision, and policy.
8. Record the verification result with the deployment.

An SBOM describes components; provenance describes how an artifact was produced. Neither should be assumed authentic solely because it exists next to an image.

## Solution 9 — Artifact promotion

1. Build the image once.
2. Scan and test the built image.
3. Push it to a restricted registry and record the immutable digest.
4. Deploy that digest to staging.
5. Store smoke-test and security-test evidence against the same digest.
6. Obtain the required release approval.
7. Verify the approved digest and deploy that same digest to production.
8. Retain the previous known-good digest and confirm it remains available for rollback.

Rebuilding can produce different bytes because of changed base images, dependencies, build inputs, timestamps, or tooling. The same source commit is not necessarily the same artifact.

## Solution 10 — Example registry access matrix

| Identity | Read | Write | Delete | Promote/deploy |
|---|---|---|---|---|
| Developer | Development packages as needed | Development packages if needed | No by default | No production access |
| CI build job | Dependencies/base images | Publish build output | No | No |
| Release manager | Release metadata and artifacts | Limited release metadata if required | No by default | Approve release according to policy |
| Production deploy job | Pull approved artifact | No | No | Deploy approved digest |
| Security auditor | Read artifacts and evidence | No | No | No |

Use platform-specific roles to implement these distinctions. Avoid giving a general build identity delete permissions that could remove released or rollback artifacts. Separate approval from execution where practical.

## Solution 11 — Retention policy example

| Class | Example policy | Safeguard |
|---|---|---|
| Pull-request builds | 7–14 days | Delete after review use ends |
| Nightly builds | 14–30 days | Keep enough history for regression analysis |
| Release candidates | Until decision plus defined buffer | Preserve evidence required for audit |
| Production releases | Support lifetime plus policy-defined retention | Keep rollback artifacts available |
| SBOM and provenance | Retain with the release record | Link to exact artifact digest |
| Audit logs | Organization-defined retention | Access control and tamper resistance |

These durations are illustrative, not universal. Define ownership, deletion permissions, exceptions, legal obligations, and a process for restoring artifacts if required.

## Solution 12 — Mini-project checklist

A strong submission includes:

- A clear artifact lifecycle from reviewed commit to production.
- Reproducible or controlled build inputs.
- Versioning that links releases to source revisions.
- Integrity verification against a trusted value.
- Least-privilege registry permissions.
- Scanning and an SBOM for relevant releases.
- Authenticated provenance or signing where supported.
- Digest-based artifact promotion.
- Retention that preserves active release and rollback artifacts.
- A threat review covering registry compromise, tag overwrite, credential exposure, and untrusted build inputs.

## Final review checklist

- [ ] Artifacts are traceable to source and build metadata.
- [ ] Tags are not treated as immutable unless enforced.
- [ ] Digests/checksums are verified against trusted records.
- [ ] Registry write and delete permissions are restricted.
- [ ] Build evidence is associated with the exact artifact.
- [ ] The same artifact is promoted between environments.
- [ ] Retention and rollback requirements are explicit.
