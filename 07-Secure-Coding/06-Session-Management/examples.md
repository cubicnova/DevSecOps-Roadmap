# Session Management — Examples

These examples illustrate design principles. Adapt syntax to your framework and use its maintained session library.

## 1. Secure cookie shape

```http
Set-Cookie: __Host-session=<opaque-random-id>; Path=/; Secure; HttpOnly; SameSite=Lax
```

Notes:
- Replace the placeholder with an opaque identifier generated by a secure session library.
- `__Host-` requires `Secure`, `Path=/`, and no `Domain` attribute.
- `SameSite=Lax` is an example, not a universal choice; evaluate the app's authentication and navigation flows.
- HTTPS is required. Use CSRF protections where applicable.

## 2. Rotate the session after login

```python
def login(request, username, password):
    user = authenticate(username, password)
    if not user:
        return generic_login_failure()

    # Framework-specific pseudocode:
    request.session.cycle_key()
    request.session["user_id"] = user.id
    request.session["authenticated_at"] = current_time()
    return redirect_to_dashboard()
```

`cycle_key`, `authenticate`, and session persistence are illustrative placeholders. Use the equivalent API documented by your framework. Ensure the old identifier cannot continue to authenticate as the newly logged-in user.

## 3. Logout must invalidate server-side state

```python
def logout(request):
    # Framework-specific pseudocode: invalidate server-side session data.
    request.session.flush()
    response = redirect_to_login()
    response.delete_cookie("__Host-session", path="/")
    return response
```

Deleting the cookie helps clear the browser copy; server-side invalidation is essential when sessions are backed by server state. Use the correct framework API and cookie name.

## 4. Expiration policy

Example policy to adapt to risk:
```text
Idle timeout: 20 minutes for a sensitive administrative console
Absolute timeout: 8 hours
Reauthentication: before changing MFA, recovery details, or payment settings
```

These are sample values, not universal standards. Choose and document values based on data sensitivity, user workflow, regulatory obligations, and threat model. Enforce timeouts server-side.

## 5. Avoid session identifiers in URLs

**Risky**
```text
https://example.test/account?sessionid=abc123
```

URLs can leak through browser history, referrer headers, server logs, screenshots, and analytics. Prefer cookies or an appropriate authorization header for the architecture.

## 6. CSRF protection

For cookie-authenticated state-changing requests:
- Use a framework's built-in CSRF protection.
- Do not treat `SameSite` alone as a complete defense without evaluating the application's context.
- Consider validating `Origin`/`Referer` where appropriate.
- Avoid state-changing `GET` requests.
- Test that missing or invalid CSRF tokens are rejected.

## 7. Revoking sessions after account events

Define policy for:
- Logout
- Password reset or password change
- MFA reset or factor removal
- Account recovery
- Role/privilege changes
- Suspected compromise
- Administrator-initiated revocation

For high-risk events, invalidate sessions or require reauthentication according to the threat model. Record sanitized audit events without raw session values.
